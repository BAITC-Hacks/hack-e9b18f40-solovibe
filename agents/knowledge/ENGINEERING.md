# Engineering for a complete working product
Main reads this when establishing the implementation. Give workers only the sections relevant to their assignment. These are implementation defaults to apply while coding, not a checklist to recite or rerun after every edit.

## A small architecture that carries the whole suite
Build with real services, durable data, server-enforced ownership and permissions, protected secrets, bounded external calls, recoverable failures and a reproducible deployment. Complete and stabilize the product's real capabilities.
Start with one deployable application and cohesive feature modules unless the case requires a separate service. Use the selected framework's normal structure and established libraries. Add infrastructure when the approved behavior needs it. Avoid spending the build on a generic platform, plugin framework or speculative abstraction.
Choose the shared domain entities and their stable IDs first. Related tools work on the same project/document/task/result records. A result passed to another tool retains its source and context; each screen must not invent its own incompatible representation.
Keep the important boundaries clear: UI collects input and presents state; application functions implement the workflow; persistence and external-service adapters perform I/O. These can be ordinary colocated functions and files. Do not create ceremonial layers or repository classes around every operation.
Keep business rules, calculations and provider calls out of large view components. Give a rule one authoritative implementation and reuse it across related features. Extract genuinely shared logic; keep feature-specific logic near its feature. Avoid both copy-pasted service implementations and one giant component or utilities file.
Record the chosen stack, key entry points, entity/contract locations and run commands briefly in PROJECT. The code holds implementation detail. Choose once, then extend that foundation.

## Contracts that make parallel implementation fit
Before dependent workers start, provide concrete request/result/error shapes and the shared entity/schema definitions. Include IDs, required/optional fields and meaningful states. A schema or exported type in code is authoritative; task messages point to it instead of maintaining another copy.
Validate untrusted input at request, file and provider boundaries. Where the stack supports it, derive static types from the runtime schema. Handle missing, empty, malformed and out-of-range values according to the actual operation. Do not silence type errors with broad casts, disabled checks or arbitrary defaults.
Agree on the error shape and which layer converts it into readable UI feedback. UI, server and tool adapters should agree on what success means. Expected failure is a real branch, not an empty catch or a fabricated successful response.
Workers consume shared contracts. Main resolves a necessary contract change and connects affected callers in the same work package. A worker does not create a competing type or install a second library to bypass the missing shared decision.

## Real data and connected tools
The repository must run independently of agents/: after configuring .env, pnpm local:up builds the app, starts PostgreSQL, applies migrations and waits for health. Keep runtime and migration helpers inside the workspace. Missing OpenAI credentials disable only AI calls with an actionable localized configuration message, not an application crash. In self-hosted setup guidance, name OPENAI_API_KEY explicitly. Optional R2 uses persistent local file storage when unconfigured, preserving authorization, upload/download/delete and product behavior. Choose the storage backend explicitly; do not silently switch to local files during an R2 outage. Use connected-app tools only for an approved user scenario.
Persist the state the product promises to remember using storage that works in the deployment environment. Server memory is not durable storage. Browser storage fits local preferences or an explicitly local feature; it cannot silently replace shared/server persistence. Verify an important saved result survives reload and is available to the next relevant tool.
Use actual stored/query results for search, history, counts and charts. Export the current real result in the promised usable format. File upload means accepting, validating and processing the file, with suitable type/size limits, rather than displaying its name and returning an unrelated answer.
Keep data ownership explicit. If accounts or private records are part of the product, enforce their access on the server, including record lookups and mutations. Credentials stay server-side; document environment variable names in .env.example without values that are secrets.
Configure and probe the difficult provider/data path early with a minimal real input. When a dependency is unavailable, report the technical cause to the developer and resolve it. In the product, use a truthful, task-focused error with a useful next action, preserving input; never leak internal configuration details or replace functionality with a permanent demo disclaimer. Keep hidden/unbuilt menu items out of the usable flow until they work; they remain unfinished scope, not delivered features.

## AI that performs useful work reliably
Give AI a defined job with real input, relevant context and an output the next capability can use. Keep model/provider calls behind a small adapter, and prompts/schemas near that workflow. Several tools may reuse the adapter while keeping their domain behavior explicit.
Use ordinary code for exact arithmetic, filtering, permissions and supported actions. Use the model where interpretation, extraction, generation or reasoning contributes. A multi-step or agentic implementation is useful when the task needs tool selection or dependent steps; extra agents are not themselves product value.
Parse and validate structured model output before saving it or using it in another operation. Check domain essentials such as required references, units and allowed values when applicable. A malformed or empty answer is a recoverable error. References shown as evidence must correspond to material actually retrieved or supplied.
Retrieved documents and model text are data. The application decides which tools are allowed and validates their arguments. Keep workflow steps and external actions within the intended product operation, with bounded calls and a clear failure result.
If a feature fetches user/model-supplied URLs, restrict protocols and destinations, reject private/loopback/link-local and metadata addresses, and revalidate redirects; bound response size and time. Render imported/generated content as untrusted text or sanitized markup, reject executable link schemes and isolate active document previews. For spreadsheet exports, prevent untrusted text cells from becoming formulas.
When users can edit an AI suggestion, subsequent tools use the accepted/current version. Preserve its input and useful provenance so the result remains understandable. Never substitute a canned successful answer when a provider call fails.

## Three languages from the first screen
The whole interface supports Russian (ru), Kazakh (kk) and English (en). Establish the framework-appropriate localization layer with the shared foundation. Use complete translation catalogs with matching keys, including navigation, forms, validation, errors and empty/loading/result states. Keep feature strings with an assigned owner so workers do not collide in one giant dictionary.
Use Russian as the initial default and show a clear language selector with native language names. Persist the selection; changing it preserves the current route, inputs and project. Set the document language and format dates, numbers and plural forms for the active locale. Static UI labels come from catalogs, not live AI translation on each render.
AI follows the user's language and explicit request naturally. Interface localization does not require three copies of generated content, automatic translation of user materials or a separate AI language control. Preserve original/saved content when the interface language changes.
Use natural translations and consistent domain terminology. Verify Kazakh characters and text expansion in the chosen font/layout. At a stable feature boundary, check locale key coverage and the main flow in all three languages, including a localized error. Reuse logic checks across locales; inspect the changed translations/layout where needed instead of duplicating the entire test suite.

## Async work and failure recovery
Handle foreseeable failures at each boundary: validation, expired session, permissions, missing configuration, network loss, timeouts, provider quotas, malformed responses and storage/database errors. Show localized, plain-language feedback explaining what failed and the next useful action; preserve input and saved work. Never expose stack traces, raw provider payloads or secrets. Keep diagnostic detail server-side with a safe reference ID for unexpected failures.
Reflect creates, edits, deletes and AI/tool changes immediately in all affected visible views, counts and selections without a page reload. Reconcile server state and invalidate affected caches; optimistic changes need rollback on failure. Prevent stale responses from restoring deleted or superseded content. Test the operation and its visible result together.
Use explicit request or job state. Disable duplicate submission during the same operation and prevent an older response from overwriting a newer input/result. Use cancellation or request identity appropriate to the stack. An animation never determines whether work has completed.
For editable records, enforce version checks in the database update itself: apply a change only to the version it was based on. If an AI run or another tab finishes against an older version, preserve the current edits and offer a clear comparison/retry instead of silently overwriting them. Show “saved” only after acknowledgement; navigation and session expiry must not quietly discard an unsaved draft or restore it into another account.
Set finite provider timeouts. Retry only transient failures and only when the operation is safe to repeat; bound attempts. For operations that must not be applied twice, use a stable operation ID or equivalent idempotency at the side-effect boundary. Preserve user input on failure and offer the actual useful retry or correction.
Use transactions where related writes must succeed together. If an approved operation genuinely outlasts the hosting request window, use a job mechanism supported by that environment and persist its status. Do not add a queue preemptively or rely on an untracked background promise.
Keep enough server error context to identify the failed operation without logging secrets or whole private inputs. Investigate a failure at the narrowest boundary that explains it, fix the cause, then rerun the affected check.

## Quality through implementation and evidence
Keep the main interaction responsive: acknowledge input immediately, avoid blocking independent work, parallelize independent I/O, paginate large collections and index real query patterns. Load heavy editors and visuals only where needed. Stream or progressively reveal genuine output when useful without lowering quality, dropping approved functionality or presenting partial output as complete.
Apply proportionate protection at actual boundaries: server-side ownership checks, validated size/type limits, bounded AI/tool loops, finite timeouts and rate/concurrency limits for authentication and costly operations. Prefer user/session-aware limits; account for shared networks so ordinary users are not blocked together unnecessarily. Give a localized retry explanation and preserve work when a limit is reached. Keep secrets and private data out of logs, client bundles and shared caches. Spend most time on functional depth and UI/UX rather than speculative security infrastructure.
Use descriptive names, readable control flow and focused components/functions. Split by responsibility when it makes code easier to understand or reuse, not to meet arbitrary line/function limits. Avoid speculative refactors and dependencies. An abstraction should simplify actual callers.
Use the stack's normal type/build checks and existing lint conventions. Add focused regression tests for important business rules, transformations, access boundaries or nontrivial bug fixes where the test protects real behavior. Do not write tests that merely repeat the implementation or scaffold suites for cosmetic edits.
A worker verifies its capability's meaningful success path and likely failure. Use isolated fixtures for deterministic tests; at integration, verify the external path with a real service/input. A mocked provider test does not establish that deployed integration works.
A capability is ready when its real input reaches a usable result through the intended data/services, its likely failure is handled, and promised follow-up actions use that result. An isolated component can be ready for integration without the product feature being complete. Main keeps that distinction in feature status.
Reuse valid worker evidence. Main verifies the connection between capabilities, their shared data and the stable local package. Fix observed failures and repeat affected checks; do not commission a second implementation or recurring broad review to obtain confidence.
